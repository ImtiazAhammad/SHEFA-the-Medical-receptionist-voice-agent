## Vision

### 10x Check

The draft plan made the dashboard the product. A dashboard is a surface people check
weekly, and this wedge's value lands the moment a patient calls and nobody is at the
desk. A product that only reports what happened is a product someone cancels.

The 10x version's atomic loop is: **a captured lead reaches a human in under 60
seconds, with a correction path when the agent gets it wrong.** The console is the
system of record for that loop, not the delivery mechanism for it.

### Platonic Ideal

The clinic owner opens one screen and knows, in Bangla, whether their line is covered
right now, what was said last night, and who is waiting for a callback — and the desk
was already texted while they slept. Nothing is entered twice. Nothing is wrong that
cannot be corrected in one tap. The agent's verification state is visible, so a human
knows when to trust it and when not to.

## Corrections Applied After Review

The reviewer scored this 5/10 and returned 15 issues. Resolutions:

- **Take-over (was a noun, now a mechanism).** Ring the desk phone via the existing
  `<Dial>` transfer. Not a browser leg. See "Take-over lifecycle".
- **Confidence (was unimplementable, now honest).** Per-field confidence is NOT
  available: `STTResult.confidence` (`models/base.py:55`) is one utterance-level
  float, and it is meaningless at two of three providers (`openai_stt.py:52` sets it to
  `no_speech`, a speech-presence probability; `elevenlabs_stt.py:40` hardcodes `1.0`).
  Only `whisper_local.py:21-56` derives anything, at segment granularity. Shipping
  instead: a **binary `callback_number_verified` flag** from the read-back confirm,
  which costs ~zero and is the honest signal. The existing `repeat_threshold: 0.5`
  repeat-prompt (`configs/default.yaml:177`) is the working mitigation and is reused,
  not duplicated.
- **Browser auth (was missing, now a line item).** See "Browser auth model".
- **Persistence engine (was a non-sequitur, now reconciled with existing init).** The
  "retrofit is a migration project" argument was wrong — the repo has no migration
  tooling at all. The stores today self-heal with `CREATE TABLE IF NOT EXISTS`
  (`store/calls.py:18-30`, `store/audit.py:26-51`) and there is no `ALTER` path, no
  `schema_version`, and no downgrade story.

  Shipping: a **`schema_version` table plus an ordered, forward-only migration list on
  raw `sqlite3`** (consistent with dep-dropping, eng M3). Concretely, migration `v1`
  reproduces the *current* `calls` and `audit_log` schemas exactly, so an existing dev
  DB adopts `schema_version=1` with no data movement; `v2+` adds `clinics`, `leads`,
  `lead_corrections`. Each migration runs inside a transaction, records its id on
  success, and aborts the boot on failure rather than starting half-migrated. Store
  `__init__` calls the runner instead of `executescript`. **Forward-only: no
  `downgrade`.** A `down()` that silently drops a PHI column is worse than a manual
  `sqlite3` restore, and the dev data is disposable by construction.

  The true justification for building fresh rather than retrofitting: **there is no
  production data to backfill**, so the schema is free to be right the first time.
- **Transport (was a false premise, corrected).** The only 5-second poll in the repo is
  **client-side** — `static/index.html:515` (`setInterval(refreshSessions, 5000)`) —
  and it targets `/api/v1/sessions`, which this plan retires. The backend has no poll
  loop. So v1 is not a new mechanism at all: it is rewriting that one existing loop.

  Shipping **2s polling of a tenant-scoped `/api/v1/owner/live` snapshot**. Rationale:
  pilot concurrency is 1-2 calls (`docs/designs/shefa-safety-net-wedge.md`), one owner
  supervises one call, and a 2s snapshot is indistinguishable from streaming to a human
  watching. It adds no new transport, reconnection, or proxy surface. SSE or a shared
  event bus is deferred to clinic 2, when concurrent-call supervision actually bites.

  Two honest notes: the "supervisor registry" is **not** greenfield infrastructure —
  `CallControl` (`telephony/control.py:49-99`) is already a process-global registry of
  live legs, populated at `twilio.py:291`, and `active_call_sids()` already yields the
  call list. The work is widening leg objects to publish turn/state, not building a
  registry. And it is **process-local**: `uvicorn.run(...)` at `main.py:470` pins no
  worker count, so more than one worker would break the snapshot endpoint. Single worker
  is a stated deployment constraint, not an accident.
- **Sessions endpoint conflict (resolved).** `TODOS.md:29` tracked a 410 deprecation for
  `/api/v1/sessions`. This plan **honours** that deprecation: the console reads from
  the store, never from live process memory. Same conclusion the prior phase reached,
  and it removes the disjoint-`SessionManager` bug class entirely.
- **PHI (was a contradiction, now addressed).** `store/calls.py:23` deliberately stores
  `caller_phone_hashed`. A `Lead` needs the number in plaintext to be dialable, which
  is the surface the existing schema avoided. See "PHI and retention".
  *Verification note: the second reviewer claimed no encryption dependency exists. That
  is wrong — `cryptography>=44.0.0` is declared at `pyproject.toml:24` and
  `ComplianceConfig.encryption_algorithm = "AES-256-GCM"` is already configured at
  `settings.py:260`. What is true is that **no code uses either yet**: the algorithm
  string is declared and never read. So field-level AES-256-GCM on `callback_number`
  using the existing dependency is achievable, and is scoped as a deliverable rather
  than claimed as a property.*
- **i18n mechanism (was undecided, now decided).** Client-side string table, not
  Jinja server-rendering. For a Bangla-primary toggleable console with no SEO need this
  is the smaller change across six screens, and it keeps the app a static bundle served
  by the existing `StaticFiles` mount. `jinja2` is then dropped from `pyproject.toml`.
- **Multi-tenancy (re-scoped honestly, then expanded by user decision).** The reviewer
  called tenancy-from-day-one YAGNI against a written halt gate. The user's position:
  no investment, everything local, and a product that works is what you approach a

## Mechanisms

### Browser auth model

Every screen is blocked until a browser can hold a credential. Shipping: **bearer token
entered on a login form, held in memory only (never `localStorage` — PHI plus XSS),
re-entered on reload.** No session cookie, so no CSRF posture change. The owner types a
token once per browser session. That is friction, and it is the right friction for a
medical console on a shared clinic machine. A signed magic-link path is deferred.

**No route becomes public. This is the load-bearing constraint, and round 2 got it
wrong.** T7's bar is explicit and deliberate: an unauthenticated request gets 401/403 on
*every* route, including `/health` and `/` (`tests/unit/test_api_auth.py:1-10`), and
`test_an_unauthenticated_request_is_refused_everywhere` (`:81-93`) walks the **live**
route table asserting no route serves without a credential. A public `PUBLIC_PATHS`
allowlist breaks three of those tests outright and publishes the whole dashboard bundle
to anonymous callers. It is also, honestly, a weakening of a codified invariant
presented as posture-preserving. Rejected.

Instead, the shell is served **behind the existing gate**:

1. `GET /login` requires a valid bearer token, exactly like `/dashboard` does today —
   it is declared in `ROUTE_PERMISSIONS` (`main.py:131-143`) with a real permission
   (`sessions:read`), not exempted.
2. The page ships with **no** bundle dependency. Its CSS is inlined and it needs no
   static assets, so nothing new is published and `/static/*` stays protected (the
   existing test at `:123-126` keeps passing untouched).
3. The owner pastes a token minted by `sefa token mint` (`cli.py:162`). The form
   **verifies it before storing it** by calling an existing authenticated endpoint
   (`/api/v1/config`, which requires `config:read` at `main.py:141`). Wrong token → 401
   → clear error, nothing stored. Correct token → held in a JS variable only.
4. The console shell then loads normally, and every `fetch` carries
   `Authorization: Bearer <token>`.

Consequence, stated plainly: a first-time owner must already hold a token to see the
login page. That is fine — tokens are minted by us, and the pilot clinic gets one in
setup. The alternative (public login page) trades a codified, tested security invariant
for cosmetic convenience, which is a bad trade in a medical app. A future
password-or-magic-link flow can introduce a single narrow public route with a
deliberate test-amendment, when there is a real second user.

Every existing auth test keeps passing unchanged. New test: an in-memory-only token
round-trips to `/api/v1/config`, and `localStorage.length` stays 0 after a successful
login.

### Coverage status (the first screen, now defined)

Two separate lines, never merged into one word:

```
in_open_hours(now)              := now ∈ clinic staffed hours, in clinic TZ (Asia/Dhaka, no DST)
escalation_roster_configured    := len(on_call_numbers) > 0        # time-invariant
```

**Both are computable from config alone, and only because Child 3 adds the schedule
config.** Today `EscalationConfig` (`settings.py:209-218`) has only
`on_call_numbers: list[str]` and **no window field at all** — that is this plan's own
Finding #2. So:

- `in_open_hours` becomes computable **only after** the clinic-hours config lands
  (Child 3). Until then the console does not compute it and does not pretend to.
- `escalation_roster_configured` is computable **today** and reduces to exactly what
  `on_call_target()` already does (`control.py:102-112`). It is deliberately
  time-invariant: a roster that is populated at 3am is still "configured", and the plan
  does not claim otherwise.

Round 2 defined the escalation term as "roster non-empty **and** inside a staffed
window", which is not computable from any existing config. The window clause is dropped
rather than given a fictional data source.

**The system still cannot determine whether a human is reachable** — that needs presence
or a calendar, neither of which exists. The console therefore never merges these into a
single word like "covered"; it shows them as two distinct facts, because "a roster is
configured" and "a human is reachable" are different promises. When the roster is
empty: "এখন কেউ নেই — শুধু এখানেই উত্তর দেওয়া হবে" ("nobody is there right now — only the
agent will answer").

### Take-over lifecycle

**Take-over is terminal. This is an architectural consequence, not a product
choice.** `CallControl.transfer` (`telephony/control.py:70`) posts a `<Dial>` TwiML to a
*separate* leg via the Twilio REST API (`twilio.py:180`). It does not move the caller's
media stream. The agent's own media stream is bound to its WebSocket, and
`twilio.py:313-325` unconditionally does, in a `finally`:

```
pipeline_task.cancel(); await pipeline.cleanup(call_sid); control.release(call_sid)
```

There is no suspend path, and adding one would mean holding a per-call pipeline alive
outside its own WebSocket lifecycle — a registry, a keepalive, and a resume protocol,
for a case where resuming mid-conflict is a worse failure than not resuming.

So the honest lifecycle, using only what exists:

1. Owner clicks take-over on a live call.
2. `CallControl.transfer(call_sid, to)` dials the on-call number. No new telephony code.
3. The human half of the call runs on the desk-phone leg. **The console cannot record
   it** — that is Twilio's leg, not ours. The console states this plainly rather than
   showing a stale transcript that implies live monitoring.
4. No-answer: if the desk leg does not connect within the ring timeout, the console
   shows `takeover_failed`. Recovering the caller to the agent is **not possible** —
   the agent's leg is already gone. The caller gets the provider's voicemail or a
   dropped call. This is a real limitation of desk-dial take-over, recorded here rather
   than papered over.

**The telephony half uses only what exists; the persistence half is new wiring.** The
transcript cannot simply be "sealed" with today's code, and round 2 claimed otherwise:

- `twilio.py:316` `finally` runs only when `iter_text()` exits, so the pipeline is
  still live after take-over fires.
- `SessionManager.save()` (`manager.py:174`) is a plain overwrite, called once per turn
  from five sites in `voice_pipeline.py`. Post-take-over turns overwrite the record.
  There is no seal flag.
- `CallSession` (`manager.py:45-50`) has no `resolution_source` field, and `handed_off`
  is not a declared state.
- With the shipped default `backend: "memory"` (`configs/default.yaml:72`) the
  transcript lives in the *pipeline's own* `SessionManager` (`voice_pipeline.py:94`),
  disjoint from the app's, and `pipeline.cleanup()` persists nothing.

So `seal_at_handoff(call_sid)` is a **named deliverable**, not a description: pull the
live session from the pipeline's manager, write a terminal row
(`resolution_source="human"`, transcript, `handed_off`) to a durable store, set a
per-call sealed flag that makes later `save()` calls no-ops **for that record**, with
flag-before-write ordering so a racing turn cannot resurrect it. It depends on the
persistence wiring below existing first.

**To get suspend-and-resume, a browser `<Client>` leg is required** (deferred). That
would put the human on our side of the boundary where the media stream and the
transcript are ours. Until then, take-over is a handoff, not a co-pilot.

A `CallLeg` interface abstraction (already present at `telephony/control.py:23-46`)
takes a browser-leg implementation later without changing callers.

### Lead verification and correction

- `callback_number_verified: bool` — set by the read-back confirm step (caller states
  the number, agent repeats it, caller confirms). This is the real quality signal.
- `capture_confidence` per field is **explicitly a non-goal** — the STT layer cannot
  supply it (§Corrections Applied). Stated here so nobody assumes it exists.
- Correction: owner edits any field in place; a `lead_corrections` row records field,
  old value, new value, principal, timestamp.
- On correction: any in-flight notification for that lead is invalidated and re-queued,
  because texting a number that was wrong reaches a stranger.
- **Corrections do NOT feed back to the model in v1.** They are an audit record and a
  data-quality signal. Few-shot correction files are deferred to clinic 2. Stated
  explicitly so the "correction path" is not read as a learning loop.

### PHI and retention

- `Lead.callback_number` is plaintext in the application (it must be dialable —
  hashing is not an option). Therefore it is **field-level encrypted at rest with
  AES-256-GCM**, using the already-declared `cryptography` dependency
  (`pyproject.toml:24`) and the already-configured `ComplianceConfig.encryption_algorithm`
  (`settings.py:260`, currently declared-but-unused). Key material comes from an env
  var, never the repo. Field-level rather than whole-DB because only this column needs
  it and `calls` deliberately hashes. Whole-disk encryption remains Child 3 owner-ops
  (`TODOS.md:37`).
- Transcripts are PHI too and are **not** encrypted at the field level in v1; they
  inherit the full-disk encryption that T7 already promoted. Stated so the gap is
  explicit rather than implied.
- `leads` gets the same `deleted_at` / `deleted_by` tombstone pattern `calls` already
  implements (`store/calls.py:109-128`).
- Per-entity retention for leads overrides the 2555-day store default
  (`ComplianceConfig.data_retention_days`, `settings.py:262`). The wedge doc commits to
  T+14 deletion after the trial week unless the owner opts in.
- `callback_number` is masked in every list view; full value only on the lead detail
  screen, behind the same auth as the transcript. Masking **extracts** `mask_phone()`
  out of the existing `mask_phi()` rather than calling it directly: `mask_phi` is
  documented "for logging" (`compliance.py:38`) and imports `audit` at module load
  (`compliance.py:13`), so reusing it directly would couple lead-list rendering to the
  log ruleset — someone tuning `_PHONE_RE` (which exists precisely because it would
  otherwise match a slice of the BD caller ID) would silently change the UI.
  `mask_phi()` then calls `mask_phone()`. One implementation, two callers, no
  behavioural change to logs.
